## Overview

InteliScrap AI is an **offline-first Progressive Web Application (PWA)** that helps informal waste recyclers (*Baban Bola*), laboratory cleaners and office cleaners across Northern Nigeria identify scrap materials, detect hazardous substances and determine fair market prices — all without internet access.

The app runs an on-device ONNX image classifier straight from the browser: snap a photo, get the material type, its safety hazards and a fair price — covering Nigeria's major official and regional languages. When the on-device model is unavailable and the phone is online, the backend calls a vision model over **Ollama**. If neither is reachable, the app honestly asks the collector to select the material manually — it **never fabricates** a result.

### Core Problem

- Waste pickers handle toxic e-waste without knowing the dangers
- Middlemen exploit lack of material knowledge to underpay
- No access to real-time scrap pricing

### Solution

- Snap a photo → on-device AI (or server vision model) classifies the material → shows fair price → reads safety warnings in the local language
- Works offline via on-device ONNX + cached prices; manual material selection as a last-resort fallback
- PWA installs on any smartphone; feature-phone users get USSD registration, location and SMS pickup notifications

> [!NOTE]
> Every analysis result carries a `source` field (`onnx` · `server` · `manual`) plus a confidence score, so a collector can always tell whether they are looking at a real inference or an honest manual pick.

## Key Features

- 📸 **Snap-to-identify** — camera capture or image upload, classified in the browser with `onnxruntime-web` (WASM), no round trip required
- 📴 **Offline-first** — service worker caching, Dexie/IndexedDB scan store and a sync queue that uploads when connectivity returns
- 🛡️ **Hazard detection** — corrosive acid, lead poisoning, mercury exposure and 12 more hazard classes with colour-coded severity badges
- ⚖️ **Fair pricing** — material → price-per-kg matrix in Naira, cached locally and reconciled on every sync
- 🗣️ **Local-language voice** — read-aloud TTS in Hausa and Nigerian Pidgin via a Google TTS proxy, with Web Speech fallback
- 🤖 **Honest AI fallback** — bundled ONNX → server `/api/v1/analyze` → manual picker (never a mock)
- 📱 **PWA + feature phones** — installable app for smartphones, USSD shortcode + SMS outbox for feature phones
- 📍 **H3 dispatch** — Uber H3 hex-grid, ring-by-ring collector matching with haversine ranking
- 📵 **No-GPS fallback** — hub/area presets + an offline Zaria gazetteer keep collectors and sellers matchable when GPS is denied or unavailable; such offers are labelled *approximate*
- 🏦 **Hub traceability** — recycling-hub daily buy requests, live `fulfilled_kg` progress, subscriptions and EPR compliance exports
- 📊 **Role dashboards** — collector, household, hub, partner, impact and sales-report views drawn with dependency-free SVG charts

> [!TIP]
> Fastest path to a working demo: `docker compose up` starts the FastAPI backend, the Vite frontend and PostGIS-backed PostgreSQL in one command.

## System Components

### Frontend (React PWA + Vite + TypeScript + Tailwind)

- **CameraCapture** — activates device camera or accepts image upload
- **vision/visionEngine** — on-device ONNX scrap classifier (runs in-browser via onnxruntime-web WASM)
- **services/analysis** — fallback chain: bundled ONNX → server `/api/v1/analyze` → manual material selection (never mocks)
- **ManualMaterialSelect** — honest manual picker when no AI path is available offline
- **useAudioTTS** — text-to-speech in Hausa/Pidgin via Google TTS proxy
- **IndexedDB (Dexie.js)** — offline scan persistence, survives browser close
- **PWA Service Worker** — custom workbox service worker (`src/sw.js`, `injectManifest`): precaches the app shell and caches the ONNX model + WASM runtime, API responses, and handles push notifications and background sync for offline use
- **Sync Engine** — queues scans offline, uploads when connectivity returns
- **Dark mode** — class-based theme with light/dark toggle, persisted and system-aware

### Backend (FastAPI + SQLAlchemy + PostgreSQL/SQLite)

- **Sync API** — bidirectional scan synchronization with conflict resolution (newer timestamp wins)
- **Price Matrix** — material → price per kg in Naira, cached locally
- **User Management** — phone-number-based registration + JWT auth
- **Analyze Proxy** — forwards images to Ollama (configurable model), returns structured JSON
- **USSD Handler** — feature-phone self-registration + preset-location menus (no smartphone needed)
- **SMS Outbox** — Africa's Talking SMS notifications (`sms.new_offer`, `sms.location`) with retry worker
- **H3 Matcher** — Uber H3 hex-grid dispatch of offers to nearby collectors
- **TTS Proxy** — fetches audio from Google Translate TTS, returns MP3
- **Recycling Hubs** — hub registration, hub subscriptions (yearly premium), daily buy requests with live progress tracking
- **Impact Dashboards** — summary / daily / by-material aggregates powering the role dashboards (NGO/partner data is premium-gated)
- **Compliance Manifests** — subscription-gated, network-wide traceability export for PROs / recyclers / FG (EPR audits)
- **Hub Delivery Traceability** — settled collections linked to the hub request they fulfil
- **Health Check** — database connectivity monitoring

### AI Layer (fallback chain)

1. **Bundled ONNX** — `vision/visionEngine` classifies the photo in-browser (works fully offline)
2. **Server vision model** — when online and edge inference is unavailable, the backend calls Ollama with `OLLAMA_VISION_MODEL` (default `llava:13b`, configurable via env)
3. **Manual selection** — if no AI path succeeds, the collector picks the material from the visible scrap classes; the result is never fabricated

## Analysis Fallback Chain

`services/analysis.ts` resolves the analysis source transparently:

| Path | Requirements | How It Works |
|---|---|---|
| **Bundled ONNX classifier** | `frontend/public/models/mobilenetv4_scrap.onnx` present | Runs the (ideally scrap-tuned) classifier in-browser via onnxruntime-web (WASM). Fully offline, no backend. Results carry `source: "onnx"`. |
| **Server `/api/v1/analyze`** | `navigator.onLine` + Ollama reachable | POSTs the base64 image; the backend proxies to Ollama (`OLLAMA_VISION_MODEL`). Results carry `source: "server"`. |
| **Manual selection** | No AI path available | The app never fabricates — it shows the scrap-classes grid and stores the pick with `source: "manual"` and zero AI confidence. |

Every result carries a `source` field so collectors can trust what they're seeing.

## Getting Started

### Prerequisites

| Dependency | Version | Required For |
|---|---|---|
| Node.js | >=18 | Frontend (React PWA) |
| npm | >=9 | Package management |
| **Python** | **3.11 or 3.12 (64-bit ONLY)** | Backend (FastAPI) |
| pip | >=23 | Python packages |
| Ollama | latest | Configurable server-side vision model (`llava:13b` default) |
| Docker (optional) | latest | One-command full-stack orchestration |

> [!IMPORTANT]
> **Critical Windows setup warnings**
>
> 1. **Do NOT use Python 3.14 (or pre-releases):** pre-compiled binary wheels (`.whl`) are not yet available on PyPI for Python 3.14. Installing packages like `pydantic-core` will attempt to compile from source and fail without C++/Rust tools.
> 2. **Install 64-bit (amd64) Python ONLY:** a 32-bit (`win32`) install makes packages such as `httptools` and `greenlet` fail with `Microsoft Visual C++ 14.0 or greater is required`. Download the **64-bit Windows installer (x86-64)**.
> 3. **Add Python to PATH:** tick **"Add python.exe to PATH"** on the first screen of the installer.

Optional for production: PostgreSQL 15+ (SQLite is used in development), ngrok (HTTPS demo on a phone).

### 1. Clone the Repository

```bash
git clone https://github.com/Moses2411/inteliscrap-AI.git
cd inteliscrap-AI
```

### 2. Set Up and Start the Backend

```bash
cd backend

# 1. Verify you are using 64-bit Python 3.12
py -3.12 --version

# 2. Create an isolated virtual environment
py -3.12 -m venv .venv

# 3. Activate the virtual environment
# Windows Command Prompt (cmd.exe):
.venv\Scripts\activate

# Windows PowerShell:
# .venv\Scripts\Activate.ps1

# Linux/macOS:
# source .venv/bin/activate

# 4. Upgrade pip inside the environment
python -m pip install --upgrade pip

# 5. Install backend dependencies
pip install -r requirements.txt

# 6. Run the FastAPI backend server
python -m uvicorn app.main:app --host 0.0.0.0 --port 8000 --reload
```

Verify: open <http://localhost:8000/docs> — you should see the FastAPI Swagger UI.

### 3. Set Up and Start the Frontend

Open a **new** terminal window:

```bash
cd frontend

# 1. Install Node modules
npm install

# 2. Start the Vite development server
npx vite --host 0.0.0.0 --port 5173
```

Verify: open <http://localhost:5173> — you should see the InteliScrap AI app.

### 4. Test the App

Snap or upload any image. The app runs the bundled ONNX classifier first (a bootstrap model **is** now shipped in `frontend/public/models/` — see its README for the measured numbers); if the model is missing or fails, it goes to the server `/api/v1/analyze` when online, and finally offers an honest **manual material picker** — there is no random/mock result ever.

### Docker (all three services)

```bash
docker compose up
```

This starts three containers: backend (FastAPI, port 8000), frontend (Vite, port 5173) and PostgreSQL (PostGIS 16, port 5432).

## Running with Ollama (Server Vision Model)

### 1. Install Ollama

Download from <https://ollama.com> and install.

### 2. Pull the Vision Model

```bash
ollama pull llava:13b
```

### 3. Run the Model

```bash
ollama run llava:13b
```

Keep that terminal open. Ollama serves on <http://localhost:11434>.

The model is configurable via `OLLAMA_VISION_MODEL` (and `OLLAMA_BASE_URL` for a remote Ollama host). Set them in `backend/.env`:

```bash
OLLAMA_BASE_URL=http://localhost:11434
OLLAMA_VISION_MODEL=llava:13b
```

### 4. Start Backend + Frontend

```bash
# Terminal 1: Ollama (already running)
ollama run llava:13b

# Terminal 2: Backend (inside .venv)
cd backend
.venv\Scripts\activate
python -m uvicorn app.main:app --host 0.0.0.0 --port 8000 --reload

# Terminal 3: Frontend
cd frontend
npx vite --host 0.0.0.0 --port 5173
```

### 5. How It Works

```
Upload photo → services/analysis.ts
  → ONNX edge classifier (if bundled) → done
  → POST /api/v1/analyze → Ollama :11434 → llava:13b → structured JSON → displayed
  → Manual material selection (offline, no model available)
```

Results from this path use `source: "manual"` and are presented honestly (zero AI confidence), so a pickup request can still be posted.

## Voice System (TTS)

### Architecture

```
Frontend "Read Aloud" button
  → Creates <audio> element with src="/api/v1/tts?text=...&lang=ha"
  → Vite dev server proxies /api/ to backend
  → Backend fetches MP3 from Google Translate TTS
  → Returns audio/mpeg to frontend
  → Browser plays it
```

### Fallback Chain

1. **Google TTS (via backend proxy)** — native Hausa/Nigerian English accent. Requires internet on the backend. This is what produces authentic voice.
2. **Browser Speech Synthesis** — uses OS voices with `lang="ha-NG"` or `lang="en-NG"`. On Android (target device), Google TTS provides native Hausa voices. On Windows without a Hausa language pack, it falls back to whatever is available.

### Language Support

- **Hausa** — Google TTS language code `ha`, Web Speech `ha-NG`
- **Nigerian Pidgin** — Google TTS language code `en`, Web Speech `en-NG`

The locale files (`locales/ha.json`, `locales/pcm.json`) contain full dictionaries for:

- 15 hazard types (corrosive acid, lead poisoning, mercury exposure, etc.)
- 17 material names
- 8 safety instruction templates

## Bundling a Real Scrap Classifier (Training)

The bundled edge model is what makes the app accurate and fully offline. A training pipeline lives in `training/` (see [`training/README.md`](training/README.md) for the full data spec — how many photos, the photography guide and the labelling rules):

```
training/
├── data/{train,val,test}/<slug>/    # labelled photos; slugs = copper, aluminum, pet-plastic,
│                                    #   lead-battery, brass, steel, e-waste, glass
├── dataset_check.py   # validates layout, counts, class balance and train/val leakage
├── dedupe_splits.py   # removes cross-split / cross-class duplicate images
├── train.py           # fine-tunes MobileNetV4 (MobileNetV3 fallback) → int8 ONNX + manifest
├── evaluate.py        # top-1 / top-3, per-class F1 and a confusion matrix
└── verify_model.py    # checks input/output shape + class order match classes.json
```

Run it once you have labeled photos (a few hundred per class). No photos yet? `python training/fetch_web_images.py --per-class 160` bootstraps a temporary, noisy set from the web — see [`training/README.md`](training/README.md).

```bash
pip install -r training/requirements.txt
python training/dataset_check.py --data training/data
python training/train.py --data training/data --out frontend/public/models/mobilenetv4_scrap.onnx
python training/evaluate.py --data training/data/test
python training/verify_model.py --image path/to/test_photo.jpg
```

`train.py` refuses to train when the dataset does not exactly match `classes.json` (it would mislabel every prediction) and writes the **measured** accuracy into `model.manifest.json`. Bundling guidance: aim for `macro_f1 ≥ 0.70` with no class missed; the repo currently ships a model trained on **93 real field photos** (macro-F1 0.690, top-1 0.72; 3 of 8 classes still have no photos). Collect many more photos per class and retrain. See `training/README.md` and `frontend/public/models/README.md`. Otherwise the app's server / heuristic / manual fallbacks are the honest option.

The exported model must satisfy the browser contract: float32 `[1, 3, 224, 224]` ImageNet-normalized input, one output of 8 logits whose index order equals `frontend/public/models/classes.json`. Trained output goes straight to `frontend/public/models/mobilenetv4_scrap.onnx`. The onnxruntime WASM runtime is emitted automatically by Vite into `dist/assets/` (no manual `public/ort/` copy step), and the service worker caches both the model and the runtime so edge inference keeps working offline after the first load.

### Recycling Hub + End-of-Life Traceability

Registered recycling hubs (recyclers/aggregators) publish **daily buy requests** — what quantity of which recyclable they need for that day. Collectors see it as a live public demand board:

1. A hub account registers straight after phone verification on the login screen (seller/collector accounts are promoted to `recycling_hub` too) via `POST /api/v1/hubs/register`.
2. The hub subscribes (`POST /api/v1/hubs/subscribe`, renewable `next_billing_at`) — this is the platform's primary recurring B2B revenue stream, and **an active subscription is required before any buy request can be published**. With MTN MoMo configured, the hub desk routes this through the MoMo checkout below instead of activating directly.
3. Hub posts a daily request: `POST /api/v1/hubs/requests` with `material_category_id`, `requested_kg`, and the date.
4. When a settled pickup's seller hub matches a registered hub **and** that hub has an open request for the same material, the settlement writes a `HubDelivery` (the traceability link) and adds the quantity to the request's `fulfilled_kg`.
5. When `fulfilled_kg >= requested_kg`, the request flips to `filled` automatically — the live progress board stays honest without manual entry.

### Subscription payments — MTN MoMo (Collections / Request-to-Pay)

Plans are priced **server-side** and collected with MTN MoMo's **Collections API** (`requesttopay`). The client never sets the price — it sends only a plan key, the server prices it, records a `payment_transactions` row, pushes a prompt to the payer's phone, and activates the subscription **exactly once** when MoMo reports `SUCCESSFUL`.

| Plan key | Who | Price | Entitlement |
|---|---|---|---|
| `seller_yearly` | sellers & collectors | ₦4,900 / year | Unlimited listings |
| `ngo_yearly` | NGO accounts | ₦49,000 / year | Network-wide impact **data access** |
| `epr_yearly` | PRO / EPR partners | ₦99,000 / year | Network-wide **EPR compliance data** |
| `pro` (hub) | recycling hubs | ₦25,000 / month | Publish hub buy requests |

A premium plan must match the buyer's role (e.g. a seller cannot buy `ngo_yearly`). Admins always have data access. The legacy `quarterly` plan value is still recognised for existing subscribers.

**Flow**

1. `POST /api/v1/payments/momo/checkout` with `{ plan, phone_number, purpose }` (`purpose` = `user_subscription` | `hub_subscription`). The local number is normalised to an MSISDN (e.g. `0803…` → `234803…`) and MoMo returns `202`; the response carries our `reference_id`.
2. The payer approves the prompt on their phone.
3. MoMo posts the final status to `POST /api/v1/payments/momo/callback/{reference_id}` **or** the app polls `POST /api/v1/payments/{reference_id}/refresh`, which asks MoMo directly. Either path lands in the same idempotent activation (guarded by `payment_transactions.applied`), so a callback and a poll can race safely.

**Configuration** (backend env — `backend/.env` locally, Render env vars in production)

| Variable | Purpose |
|---|---|
| `MOMO_ENABLED` | `true` to turn payments on (default `false`, so nothing calls MTN until set) |
| `MOMO_SUBSCRIPTION_KEY` | Subscription key for the **Collections** product (Products → *Collections* → Subscribe; MTN's guide says use the **primary** key). ⚠️ This is a *different* product from **Collection Widget** (a web checkout button) — a widget key will be rejected by the Collection API |
| `MOMO_API_USER` | API user UUID for Collections |
| `MOMO_API_KEY` | API key bound to that API user |
| `MOMO_BASE_URL` | `https://sandbox.momodeveloper.mtn.com` (sandbox) or the country production proxy |
| `MOMO_TARGET_ENVIRONMENT` | `sandbox`, or the country value in production |
| `MOMO_CURRENCY` | `EUR` in the sandbox; the local currency in production |
| `MOMO_CALLBACK_BASE_URL` | Public backend URL MoMo can POST to (e.g. the Render URL); blank ⇒ polling only |
| `MOMO_MSISDN_COUNTRY_CODE` | Country code used to expand local numbers (default `234`) |

**Getting the API user + key (sandbox).** Besides the subscription key you need an API user + API key. In the sandbox these are self-provisioned: sign in as an admin and call `POST /api/v1/payments/momo/provision` (debug builds only) — it returns the `api_user` and `api_key` to paste into the env above, then `MOMO_ENABLED=true` and restart.

> **Which product to subscribe to?** Server-initiated subscription charges use the **Collections** product (Request-to-Pay): the backend pushes a prompt to the payer's phone and the payer approves it. The **Collection Widget** product is a separate web checkout button (USSD/QR) and uses its own key — subscribe to **Collections** for this integration. In the sandbox, MTN's test MSISDNs (e.g. `46733123450` for success, `46733123451` for failure) can be used to exercise the full flow without a real wallet.

The UI (`MomoCheckout`) is surfaced on the Settings page (a role-aware premium card: Seller/Collector, NGO or EPR), the listing-limit upsell after a scan, the impact dashboard when an NGO hits a `402`, and the partner EPR dashboard when a PRO has no active plan. Premium-only screens show an **in-context subscribe CTA** instead of an error. When `MOMO_ENABLED=false` every one of these shows the config-driven **coming-soon popup** rather than failing.

### Compliance Manifesto (EPR) Export

PROs, recycling companies and FG/EPR auditors authenticate with their **session bearer token** against `GET /api/v1/compliance/manifesto` — access is **subscription-based** (an active EPR premium plan), not an API key. The response is a **network-wide**, read-only, auditable export of every settled collection in a date range: transaction, registered collector, material, weight, value, carbon offset and originating hub — the source-verifiable record EPR contracts require. (Machine-to-machine partner notifications still use the separate partner API key; only the EPR dashboard/compliance data moved to subscription auth.) Each manifest line also reports `carbon_kg_co2e_per_kg_used` — the per-material emission factor applied — so every tonnage-to-carbon figure is auditable. (An earlier build hardcoded copper's factor of 2.6 for every material, understating aluminium ~3.5× and overstating glass ~8.7×; `test_compliance_manifesto_uses_per_material_carbon_factor` guards the fix.)

### USSD Registration & Location (feature phones)

A collector can self-register without a smartphone by dialing the USSD shortcode:

1. Dial `*347*101#` (configurable). The first screen asks for **Consent & Registration**.
2. Reply `1` → the hub menu lists **6 preset hubs** (Samaru, Sabon Gari, Kongo, Bomo, Hanwa, Dutsen Abba).
3. Reply `1*N` → the backend creates a `collector` user, resolves the hub lat/lng + H3 hex, and confirms. The collector is now joinable for offers.
4. Registered callers reach the **Main Menu** including `4. Wurin da nake aiki` → `4*N` to change their work hub on the move.
5. When a new offer matches their hex, the outbox worker SMSes them, and they can **accept via USSD or IVR (voice callback)**.

The `ussd_handler` uses a `session_id`-based state machine (`_register_flow`, `_location_flow`) so a reply-only flow works on any feature phone. Registration only ever **creates** a collector: if the dialling number already belongs to a seller (or hub), USSD refuses rather than re-roling the account, which would otherwise orphan that user's listings.

**What USSD can and cannot do today.** A feature-phone collector can be notified, list offers and **accept** one. The flow ends there — there is no handover or weight capture over USSD, so the seller completes the pickup from the browser using the PIN the collector received. Offers read the seller's `estimated_weight_kg`, which is now **required when posting a listing**; a null weight renders as `0kg` in both the USSD list and the location SMS.

### Hexagon (Uber H3) Collector Matching

When a listing is created with coordinates, the platform dispatches it using the same **hexagonal gridding pattern Uber uses** for rider–driver matching:

1. The seller's location is bucketed into an **Uber H3 hexagon** cell at resolution `H3_RESOLUTION` (default `8` ≈ 460 m cells).
2. `h3.grid_disk(origin, k)` expands the search **hexagon-by-hexagon, ring-by-ring** outward until the dispatch radius (`DISPATCH_RADIUS_M`, default 5 km) is covered.
3. Active collectors whose stored `h3_cell` falls inside that hexagon disk are candidates — no full-table distance scan.
4. Candidates are ranked by exact **haversine** distance, filtered to the radius, and the closest `DISPATCH_MAX_COLLECTORS` (default `5`) each receive a `Pickup` in `offered` status (listing → `matched`).

Collectors keep their hex bucket fresh via `PATCH /api/v1/users/me/location`, which recomputes `h3_cell`. The `h3` index is stored on `users` (`idx_users_h3_cell`) for Postgres and the on-the-fly fallback keeps SQLite/dev working identically.

#### No-GPS fallback (`location_service`)

GPS is the primary location source, but a collector on a feature phone, or a device
with GPS denied, must not be silently dropped from dispatch. When live coordinates
are missing, the backend resolves an **approximate area centroid** instead:

1. **Hub preset** — one of the operational areas (Samaru, Sabon Gari, Kongo, Bomo,
   Hanwa, Dutsen Abba), the same set USSD onboarding uses.
2. **Address gazetteer** — a small offline map of Zaria neighbourhoods/landmarks
   (`location_service.GAZETTEER`) scanned from the free-text address, longest match
   first. No network or third-party geocoder required.

Every coordinate records *how* it was obtained (`location_precision`): `gps`,
`hub`, or `address`. Sellers and collectors who sign up with an address (or choose a
hub) are placed immediately; a real GPS fix always wins and is never overwritten by
a guess. Because area centroids are coarse, dispatch **widens the radius** for
approximate locations (`LOCATION_FALLBACK_RADIUS_MULTIPLIER`, default `1.5×`) and
ranks exact GPS matches ahead of approximate ones. Offers expose
`location_precision` so the UI labels area-level pickups **Approximate location**.

**Guarantees:** a listing is only `offered` to collectors; as soon as one accepts (via **USSD** or **IVR**), the pickup becomes `accepted`, the listing moves to `scheduled`, and all other pending `offered` pickups are no longer surfaced — the listing is unavailable to every other picker.

## Troubleshooting

| Problem | Cause | Solution |
|---|---|---|
| `Microsoft Visual C++ 14.0 or greater is required` during `pip install` | You are using 32-bit Python or Python 3.14+. PyPI lacks pre-compiled wheels for these versions. | Uninstall 32-bit Python. Install Python 3.12 64-bit (x86-64). Delete your `.venv` folder, re-create it (`py -3.12 -m venv .venv`), and run `pip install -r requirements.txt`. |
| Backend returns 502 on `/api/v1/analyze` | Ollama isn't running on port 11434 or the vision model isn't pulled. | Start it with `ollama run llava:13b` (or set `OLLAMA_VISION_MODEL`/`OLLAMA_BASE_URL`). If Ollama is off, the app falls back to manual material selection. |
| Scan shows "Manual" with no AI result | No ONNX model bundled and no server reachable. | Bundle a model under `frontend/public/models/` for offline edge classification, or run Ollama. This is intentional — the app never fabricates results. |
| `.venv\Scripts\activate` fails on PowerShell | Execution Policy blocking scripts. | Run in standard CMD (`cmd.exe`), or run `Set-ExecutionPolicy -ExecutionPolicy RemoteSigned -Scope Process` in PowerShell. |
| Camera button does nothing | Camera permissions blocked or unsupported mode. | Try selecting "Upload Image" instead. |
| TTS sounds Chinese | No native Hausa voice installed in local browser OS. | Google TTS proxy (backend) handles native voices — ensure the backend is running. |
| Scans show "Pending" forever | Backend offline or internet disconnected. | The sync button manually triggers upload once connected. |
| `pip install asyncpg` fails | Missing C++ tools on Windows. | Use SQLite (default in local development config). |
| `npm install` hangs / ETARGET error | Corrupted npm cache. | Clear cache: `npm cache clean --force && npm install`. |
